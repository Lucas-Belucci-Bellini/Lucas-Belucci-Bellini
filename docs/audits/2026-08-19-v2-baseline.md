## Resumo executivo

O repositório é um perfil/indexador público, não uma aplicação com servidor próprio. A atualização é feita por GitHub Actions. A quebra rápida do histórico não vem dos projetos acompanhados individualmente, mas do próprio `ecosystem-watch.yml`, que executa a cada hora, sempre grava um novo carimbo de varredura e incrementa `monitor_commits` antes de publicar o snapshot. Como resultado, cada execução bem-sucedida gera um commit mesmo quando nenhum dado do ecossistema mudou.

O `lang-stats.py` já possui uma proteção correta: compara o conteúdo ignorando carimbos de hora e só altera README/SVG quando os dados mudam. O problema principal está no caminho `ecosystem_watch.py` + passo de commit do workflow.

## Causa raiz e efeitos

| Categoria | Constatação | Efeito |
| --- | --- | --- |
| Causa raiz | O monitor escreve `scanned_at` em todo ciclo e soma `monitor_commits += 1`. | O estado muda sempre, então o workflow sempre encontra diff para commitar. |
| Causa cascata | O workflow publica o snapshot a cada hora. | Aproximadamente 24 commits diários mesmo sem alteração de dados. |
| Limitação atual | A execução consulta os repositórios de forma sequencial e faz chamadas `latest` + `compare`. | A duração cresce com o número de repositórios e pode atingir o timeout. |
| Fragilidade operacional | O contador do próprio monitor é misturado ao contador de projetos. | O índice mede sua atividade de publicação, não apenas mudanças do ecossistema. |
| Ponto positivo | `lang_stats.py` usa comparação sem carimbo para evitar commits sem mudança de dados. | Esse padrão pode ser reaproveitado no monitor de commits. |

## Contrato V2 proposto

A V2 mantém o formato dos arquivos públicos e adiciona uma regra de publicação: uma execução pode atualizar o estado em memória, mas só deve produzir commit quando houver alteração semântica no snapshot. O carimbo `scanned_at` deve continuar registrando a última varredura, mas não deve, sozinho, causar um commit.

O monitor deve excluir explicitamente o próprio repositório de perfil da lista de projetos acompanhados. Isso impede que o commit produzido pelo monitor seja redescoberto como uma mudança de projeto no ciclo seguinte.

A execução deve continuar tolerante a falhas parciais. Erros por repositório devem ser armazenados no snapshot, enquanto o workflow termina com sucesso se a varredura global puder ser publicada. O `timeout-minutes` permanece como limite de segurança, e a concorrência deve cancelar uma execução antiga quando uma nova for disparada.

## Critérios de aceitação

1. Uma execução sem mudança de SHA, contadores ou erros não cria commit.
2. Uma mudança real em qualquer projeto cria um único snapshot agregado.
3. O próprio repositório de perfil não aparece como projeto monitorado.
4. Uma falha HTTP em um projeto não impede os demais nem apaga o último estado válido.
5. O contador de commits do monitor só aumenta quando um snapshot é realmente publicado.
6. Testes unitários cobrem estado inalterado, projeto alterado, exclusão do perfil e erro parcial.
7. O workflow mantém `contents: write`, concorrência e execução manual, sem adicionar segredo ao código.

## Rollback

O rollback é feito revertendo o commit da V2 no `main`. Os arquivos públicos `docs/ECOSYSTEM-COMMIT-STATE.json` e `docs/ECOSYSTEM-COMMIT-MONITOR.md` podem ser restaurados pelo próprio workflow após a reversão.

## Limitações conhecidas

A integração ainda depende dos limites e respostas da API pública do GitHub. Repositórios vazios ou com conflitos HTTP 409 são registrados como erro. A V2 reduz commits e custo de histórico, mas não transforma o perfil em um serviço de deploy; produção deve ser atualizada por uma integração de hospedagem ou por um webhook autenticado separado.
